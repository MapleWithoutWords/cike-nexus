# 部门增删改查

## Problem Statement

组织管理员目前无法在系统里维护部门。`department` 与 `departmentuser` 两张表在初始迁移里就已建好，但没有任何接口能读写它们——想录入公司的组织层级、调整部门归属、或者只是看一眼现在有哪些部门，都只能直接改数据库。

同时，知识库授权（`KnowledgeRelation` 的 `correlation_type = 2`）等后续功能已经在数据模型上依赖部门，但部门本身还没有任何可用的管理入口，这些功能无从落地。

## Solution

提供一组部门管理接口，覆盖新建、修改、删除、查询：

- 管理员可以新建顶级部门或子部门，逐层搭出部门树。
- 管理员可以一次性取回完整部门树，在管理界面直接展开浏览，无需逐层请求。
- 管理员可以改名、改描述、调整同级顺序，也可以把一个部门连同其全部后代部门移动到另一个上级部门之下。
- 管理员可以删除部门，但当该部门还有子部门或还有部门成员时，系统拒绝删除并说明原因，绝不做用户看不见的连带修改。
- 部门名称在同级范围内唯一，跨级可以重复。

同时修掉三处让上述功能无法工作的既有缺陷：审计时间字段没有默认值导致插入必然失败、出参 DTO 基类没有继承 pydantic 模型导致大整数 id 序列化失效、路由层 import 拿到模块而非类导致应用无法启动。

## User Stories

1. 作为组织管理员，我想新建一个顶级部门，以便把公司的一级组织结构录进系统。
2. 作为组织管理员，我想在指定的上级部门下新建子部门，以便逐层搭出完整的部门树。
3. 作为组织管理员，我想在新建部门时填写描述，以便同事知道这个部门负责什么。
4. 作为组织管理员，我想在新建部门时可以指定排序值，以便让重要部门排在同级部门前面。
5. 作为组织管理员，我想在不指定排序值时新部门自动排在同级末尾，以便批量录入时不必每次都考虑顺序。
6. 作为组织管理员，我想在同级部门中出现重名时被拒绝并告知是名称冲突，以便避免两个无法区分的「前端组」。
7. 作为组织管理员，我想在不同上级部门下使用相同的部门名，以便「技术部 / 前端组」和「产品部 / 前端组」能够共存。
8. 作为组织管理员，我想在指定了不存在或已删除的上级部门时被拒绝，以便不会产生挂不上部门树的孤立部门。
9. 作为组织管理员，我想一次请求就拿到完整部门树，以便在管理界面上直接展开浏览整个组织。
10. 作为组织管理员，我想部门树中的同级部门按我设定的排序值展示，以便看到的顺序和我的设定一致。
11. 作为组织管理员，我想已删除的部门不出现在部门树中，以便界面只反映当前有效的组织结构。
12. 作为组织管理员，我想部门树能同时呈现多个顶级部门，以便公司存在多个并列一级组织时也能表达。
13. 作为前端开发者，我想树接口一次返回全部层级，以便渲染组织架构树、人员选择器时不用为每次展开都发一次请求。
14. 作为前端开发者，我想树节点只包含渲染所需字段，以便整棵树的响应体不被审计字段撑大一倍。
15. 作为组织管理员，我想查询单个部门的详情，以便编辑弹窗能正确回填当前值。
16. 作为组织管理员，我想在部门详情里看到创建时间、更新时间和操作人，以便追溯这个部门是谁在什么时候改的。
17. 作为组织管理员，我想修改部门的名称和描述，以便部门改名或职责调整后系统保持同步。
18. 作为组织管理员，我想单独调整某个部门的排序值，以便重排同级部门的展示顺序。
19. 作为组织管理员，我想把一个部门连同其全部后代部门移动到另一个上级部门之下，以便组织调整时不必重建整棵子树。
20. 作为组织管理员，我想把一个子部门提升为顶级部门，以便某个部门独立出来时能够表达。
21. 作为组织管理员，我想在试图把部门移动到自己的后代部门之下时被拒绝，以便不会把整棵子树从部门树上弄丢。
22. 作为组织管理员，我想在试图把部门移动成自己的上级部门时被拒绝，以便不会产生自我引用的部门。
23. 作为组织管理员，我想在移动后与新位置的同级部门重名时被拒绝，以便新位置下的名称依然唯一。
24. 作为组织管理员，我想删除已经不存在的部门，以便部门树反映组织现状。
25. 作为组织管理员，我想在部门还有子部门时被拒绝删除并被告知原因，以便一次点击不会连带删掉整棵子树。
26. 作为组织管理员，我想在部门还有部门成员时被拒绝删除并被告知原因，以便不会出现隶属于已删除部门的用户。
27. 作为组织管理员，我想删除采用软删除语义，以便误删之后数据仍在库里、可由维护者恢复。
28. 作为组织管理员，我想对不存在的部门执行查询、修改或删除时得到明确的「不存在」响应，以便区分「没这个部门」和「操作被业务规则拒绝」。
29. 作为前端开发者，我想部门 id 以字符串形式返回，以便 JavaScript 处理大整数时不丢失精度。
30. 作为后端维护者，我想审计时间字段在新增和更新时自动填充，以便新增部门不再因为 `update_at` 为空而插入失败。
31. 作为后端维护者，我想应用能够正常启动，以便部门接口可以被真实调用而不只是通过读代码自证。
32. 作为后端维护者，我想部门表结构与实体定义保持一致，以便后续的 Alembic autogenerate 不再产出意料之外的变更。

## Implementation Decisions

### 领域规则

- **`parent_id = 0` 是「无上级」的哨兵值**，表里不存在 `id = 0` 的记录。因此部门树是森林而非单根树，可以有多个顶级部门。理由与被否决的替代方案见 ADR-0001。
- **`0` 永远不是合法的部门 id。** 以 `0` 作为部门 id 传入的请求是非法参数。
- **名称在同级范围内唯一**：同一 `parent_id` 且未被软删除的部门之间不允许同名，跨级可以重名。用业务代码校验而非数据库唯一索引——软删除会让唯一索引与「已删除的同名部门」冲突。
- **删除是软删除**，置 `is_deleted = True`；所有查询过滤已删除部门。
- **删除设双重前置校验**：存在未删除的子部门则拒绝；存在部门成员则拒绝。两条都是「不做用户看不见的连带修改」的体现：不级联软删、不把子部门上提、不留下指向已删部门的悬空关联。
- **移动部门的三条校验**：目标上级部门必须存在且未删除（`0` 除外，跳过校验）；目标上级不能是自己；目标上级不能是自己的后代部门。
- **排序**：新增时未提供排序值则取同级部门 `max(sort) + 1`，新部门落在同级末尾。

### 查询与组树

- **部门树由一条 SQL 取全量、在内存中组装**：查出全部未删除部门（`ORDER BY sort, id`），按上级 id 分桶，一次 O(n) 遍历成型。不使用递归 CTE——部门是百级数据量，CTE 换来的是 MySQL 版本绑定和难读的 SQL，且组树逻辑封装在服务内部，将来数据量上涨可以无损替换。
- **子节点顺序继承 SQL 的排序**，内存组装阶段不再二次排序。
- **孤儿节点提升为顶级部门**：若某部门的上级 id 不在结果集中，将其作为顶级部门挂在树顶，并记录一条包含该部门 id 与失效上级 id 的 warning 日志。按上述删除规则这种数据不应出现，但「不应出现」的状态仍需确定行为——静默丢弃会让部门在界面上凭空消失，同时详情接口却仍能查到，两个接口自相矛盾。
- **后代判定复用同一份全量数据**：移动部门时的后代集合由内存中的上级映射自底向上回溯得出，不额外查库。

### 模块

新增：

- `DepartmentService`（应用层）——承载全部业务规则与校验，构造函数注入 `Session`，校验失败直接抛 `HTTPException`。
- `DepartmentRouter`（接口层）——只做参数绑定与转发，通过 `Annotated[DepartmentService, Depends(DepartmentService)]` 注入服务，在应用入口以 `/api/departments` 前缀注册。
- 部门 DTO 四个：新增入参、修改入参、详情出参（继承 `AuditedDto`，含审计字段）、树节点出参（仅 id、名称、描述、上级 id、排序、子节点）。树与详情用两个不同 DTO，避免整棵树携带前端不使用的审计字段。

修改：

- `Department` 实体——新增排序字段；描述字段的默认值由占位文案 `"描述"` 改为空串。
- `AuditedEntity`（审计实体基类）——创建时间与更新时间改用 `default_factory` 求值（当前写法在模块 import 期求值一次，导致同一进程内所有新记录共享同一时间戳），更新时间追加 `onupdate` 钩子。这解决了「更新时间无默认值且数据库列为 `NOT NULL`，任何未显式赋值的插入都会失败」这一阻塞性缺陷。
- `AuditedDto`（出参 DTO 基类）——改为继承 pydantic `BaseModel`。当前它未继承任何基类，因此是一个普通 Python 类：字段注解在运行期完全惰性，`field_serializer` 从不生效，「把大整数 id 序列化为字符串」这一既定约定实际上从未生效。实体基类继续使用 SQLModel，两层各归各位。
- `UserRouter`——修正服务的 import，当前从包导入取到的是模块而非类，导致应用入口 import 即抛 `TypeError`，整个应用无法启动。
- `UserService`——会话参数的类型注解由模块改为 `Session`，并移除构造函数上错误的返回类型标注。
- README——补充部门接口与数据模型说明。

### API 契约

| 方法 | 路径 | 请求 | 成功响应 |
| --- | --- | --- | --- |
| `POST` | `/api/departments` | 名称、描述、上级 id、排序（可选） | `200`，返回字符串形式的部门 id |
| `PUT` | `/api/departments/{id}` | 名称、描述、上级 id、排序 | `204` |
| `DELETE` | `/api/departments/{id}` | — | `204` |
| `GET` | `/api/departments/tree` | — | `200`，顶级部门数组，每个节点递归携带子节点 |
| `GET` | `/api/departments/{id}` | — | `200`，部门详情 |

新增接口返回字符串 id 而非裸整数——与 DTO 把 id 序列化为字符串是同一个理由。既有的用户新增接口返回裸整数，是同一个精度问题的既存实例，本次不改动用户接口契约。

修改与删除返回 `204`，不回吐响应体。

### 错误映射

| 状态码 | 场景 |
| --- | --- |
| `404` | 目标部门不存在或已被软删除 |
| `409` | 同级部门名称冲突（新增与移动共用此码） |
| `409` | 该部门存在未删除的子部门，拒绝删除 |
| `409` | 该部门存在部门成员，拒绝删除 |
| `400` | 指定的上级部门不存在、上级是自己、上级是自己的后代部门 |

### 数据库变更

一条迁移，仅涉及 `department` 表：新增排序列；描述列长度由 256 调整为 512（实体声明的是 512，初始迁移建的是 256）。

迁移由 `alembic revision --autogenerate` 生成，不手写——手写容易与 SQLModel 实际渲染的类型对不上。已逐列比对确认全项目仅此一处结构漂移，其余实体与库完全对齐，因此 autogenerate 的产物恰好就是上述两条操作，无需人工裁剪。`Knowledge` 与 `KnowledgeRelation` 未登记进 Alembic 环境，它们既不在 metadata 中、库里也没有对应表，autogenerate 两侧都看不见，不会误建也不会误删。

## Testing Decisions

项目当前**没有任何测试**：无 pytest 依赖、无测试目录、无 `conftest.py`。因此没有可参照的先例，测试基础设施需要一并建立。

### 缝的位置

**只开一道缝：HTTP 层。** 用 FastAPI 的 `TestClient` 打真实请求，通过 `app.dependency_overrides` 替换会话依赖，指向内存数据库。这是可能的最高的缝，一道就够，并且顺带覆盖了本 spec 中几个关键决定——状态码映射、id 是否真的序列化成字符串、树节点 DTO 是否真的不含审计字段——这些在更低的缝上全都测不到。

不在应用服务层单独开缝：那会跳过路由与序列化，而 `409` / `400` / `404` 的映射和 DTO 契约正是最容易写错的部分。组树与后代判定虽然是纯逻辑，也不为它们单独开缝，而是通过 HTTP 缝覆盖，以维持「一道缝」。

**代价要说清楚**：内存数据库（SQLite）不认 `BIGINT PRIMARY KEY` 的自增语义，需要在审计实体基类上为主键类型加一个 SQLite variant。这是为测试而动生产代码的一行让步，换来的是测试无需任何外部基础设施、可在任意机器与 CI 上毫秒级运行。替代方案是让测试连真实 MySQL 测试库——更接近生产，但慢、需要建库与清理，且当前数据库凭据不可用，等于测试从第一天就跑不起来。

### 什么算好测试

只断言外部可观察的行为：HTTP 状态码、响应体结构与字段值、以及后续请求能观察到的状态变化（例如删除后树接口里不再出现该部门）。不断言服务内部调用、不直接查表验证 `is_deleted` 标记——软删除的可观察后果就是「树里没了但详情仍在」，测这个后果，不测实现细节。

### 覆盖清单

围绕业务规则组织，而非围绕接口：同级重名被拒、跨级重名允许、上级不存在被拒、部门树的层级与顺序、树中不含已删除部门、多个顶级部门并列、移动到后代之下被拒、移动到自身被拒、移动后重名被拒、有子部门拒删、有成员拒删、删除后详情仍可查而树中已消失、未指定排序值时落在同级末尾、id 以字符串返回、树节点不含审计字段、对不存在的部门操作返回 `404`。

## Out of Scope

- **部门成员管理**：把用户加入或移出部门、查询某部门下的成员。本次只在删除校验中读取部门成员的存在性，不提供任何写入接口。「一个用户能否隶属多个部门」这一问题也留待该功能再定。
- **认证与鉴权**：审计字段中的操作人（`created_by` / `updated_by`）仍然为空，需等登录与 Token 机制落地后自动填充。
- **平铺分页与关键字搜索部门**：本次只提供整棵树与单条详情。
- **批量拖拽排序接口**：调整顺序走单个部门的修改接口。
- **恢复已软删除的部门**。
- **「唯一顶级部门」约束**：若将来需要公司本体作为唯一根节点，加一条业务校验即可，不需要迁移（见 ADR-0001）。
- **`Knowledge` / `KnowledgeRelation` 建表**与登记进 Alembic 环境。
- **用户模块的其余遗留缺陷**：用户查询接口仍是占位实现，用户新增接口仍返回裸整数。本次只修阻塞应用启动与阻塞插入的那几处。

## Further Notes

**存在一个环境路障**：数据库当前连不上（`Access denied for user 'root'@'localhost'`）。代码可以全部写完，但迁移脚本无法生成（autogenerate 需要连库做 diff），接口也无法真实调用验证。需要先修复 `.env` 与 `alembic.ini` 两处凭据配置——注意这是两套独立配置，改数据库时两处都要改。若测试采用内存数据库方案，则测试不受此路障影响。

**术语**：`CONTEXT.md` 以「顶级部门」为规范术语，「根部门」列入 `_Avoid_`。因为选定 `0` 为哨兵后顶级部门可以有多个，「根」字会让人误以为只有一个，从而写出取首个元素当根节点的缺陷。其余术语（部门树、上级部门、子部门、后代部门、同级部门、移动部门、部门成员）同见 `CONTEXT.md`。

**相关决定**：ADR-0001 记录了为何用 `parent_id = 0` 而非 `NULL` 或真实的根部门记录。「内存组树而非递归 CTE」刻意没有写成 ADR：它封装在服务内部，替换不影响任何调用方，不满足难以逆转的门槛。
